Lesson 01 · Windowed prefill

The mask is a work map

A mask tells you which scores to throw away. Read it one tile at a time and it tells you something far more useful: which memory you never had to load.

Your README makes a claim: at a 32K prompt, a local layer computes about 64× more score pairs than it keeps. That number is correct, and by the end of this lesson you will be able to derive it — but deriving it is not the skill. The skill is the step after it, because a kernel cannot skip a pair. It can only skip a tile.

That gap between pairs you don't need and tiles you can refuse to load is where the entire Phase 5 kernel lives. Today you learn to compute it exactly.

Vocabulary check

PV is simply attention's second matmul: the probabilities after softmax, multiplied by V. Attention is two matmuls with a softmax between them — QKT produces the scores, PV consumes them. Both are per query head, both cost 2·N·S·D FLOPs, which is why shapes.py charges 4·pairs·head_dim for the pair — a 2 for each matmul.

1 · Which 64×?

A local layer at window W = 512 lets query q attend to keys in [q−W+1, q]. So the number of pairs it keeps is Σ min(q+1, W), which for N ≫ W is very nearly N·W. The question is what you divide that by — and there are two honest answers.

Both rows are verified arithmetic, not estimates: at N = 32768, W = 512, exactly 16,646,400 pairs are kept.

DenominatorPairsKeptMeaning
N² — dense scores1,073,741,8241.55% what the naive baseline actually computes
N²/2 — causal only536,887,2963.10% what a causal-but-unwindowed kernel computes

The README's 64× is the first row, and it is the right one to quote, because the naive baseline is defined as materialising the full score matrix and then masking. But notice what just happened: half of that 64× is causality, which every attention kernel already exploits. Windowing's own contribution is 32×, not 64×. Quote the number, but know which part of it your kernel is being credited for.

2 · Tiles, not pairs

A Pallas kernel walks a grid. Each grid step handles one block of queries against one block of keys — a tile. The kernel's only real decision is: for this tile, do I issue the DMA or not? So classify every tile into three states:

  • dead — the mask forbids every pair in it. Never load it. This is block skipping.
  • partial — some pairs allowed, some not. Load it, then apply an elementwise mask, exactly as the naive baseline would.
  • full — every pair allowed. Load it and skip the masking entirely.

Take a tile covering queries [qlo, qhi] against keys [klo, khi]. Every pair in it has a diagonal offset d = q − k, and as q and k range over the tile, d sweeps a contiguous interval [qlo−khi, qhi−klo]. The mask is itself just a band, 0 ≤ d ≤ W−1. Two intervals overlap iff neither ends before the other starts — which collapses the whole thing to two comparisons:

live  ⟺  qhi ≥ klo  and  qlo − khi ≤ W − 1
full  ⟺  khi ≤ qlo  and  qhi − klo ≤ W − 1

First comparison is causality; second is the window. A global layer is the same predicate with W = ∞ — one clause simply never fires. Local and global are not two kernels.

That is the whole thing. No loop over positions, no materialised mask — two integer comparisons per tile, evaluable at trace time, which is precisely why it can become an index_map in Phase 5 instead of a runtime branch.

Verified, not asserted

This predicate was checked exhaustively against reference.attention_mask() in reference.py — 16,464 tiles across every combination of N ∈ {512, 1024, 2048}, W ∈ {128, 256, 512, ∞} and block sizes {64, 128, 256}. Zero mismatches.

3 · See it

Queries run down, keys run across. Start at seq_len 2048, local, block 256 — then switch the layer to global and watch which of the two clauses you just lost.

4 · The block size is not free

Here is the payoff, and it is the part that surprises people. The band has a fixed width, but tiles are square — so a query row's live tiles number about W/B + 1, and that +1 is pure overhead. Smaller blocks track the band more tightly:

BlockGridLive tilesLive/rowLoadedWaste
51264 × 641271.983.10%2.00×
256128 × 1283812.982.33%1.50×
128256 × 2561,2704.961.94%1.25×
—pair-level——1.55%1.00×

All at N = 32768, W = 512. Choosing B = W = 512 — the obvious, tidy choice — makes your kernel load twice the KV it strictly needs. Choosing B = 128 cuts that to 1.25×, but 128 is the v5e MXU dimension, so tiles stop amortising and the grid grows 16-fold in steps.

The win

You now have the number that Phase 5's block size must be argued against. Not "128 felt fast" but "B = 256 loads 1.50× the minimum KV and keeps tiles two MXU passes wide". That is a roofline argument, and you can make it before writing a line of the kernel.

5 · Retrieve it

Work these out rather than recognising them — evaluate the predicate on paper. Getting one wrong is more useful than getting it right by feel.
