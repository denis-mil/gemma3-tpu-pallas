Lesson 05 · Windowed prefill

The index_map that lies

Lesson 01 derived which tiles a windowed kernel may refuse to load. Four lessons later that predicate has still never run. This is where it becomes code — and the machinery it needs turns out to be machinery you already have.

You can now write a BlockSpec and defend it: which axis goes last (03), how big the block may be and whether it fits (04). What none of it can do is decline a block. The grid walks every kv tile, including the ones lesson 01 proved were dead. At Gemma 3 1B's full context that is 4096 grid steps to do 127 tiles of real work.

The thesis

Block skipping is not a mechanism. It is copy elision driven by a table. There is no skip=True flag, no sparse grid type, no new pipeline. There is an index_map that returns the same block index twice in a row on purpose, and the rule you already learned in lesson 03 does the rest.

1 · Getting a table in before the pipeline starts

An index_map runs at trace time, before any data exists in VMEM. So it cannot read K to decide which K to fetch — that is the chicken-and-egg problem that makes data-dependent indexing look impossible. Pallas breaks it with one escape hatch:

Scalar prefetch allows you to pass in a small amount of data into SMEM ("scalar memory") that is loaded before the start of the pipeline ("prefetch"). Because this data is loaded before the pipeline, it is available for use in the index_map for each BlockSpec, allowing you to perform data-dependent indexing calculations. — Scalar Prefetch and Block-Sparse Computation

Three mechanical facts, and they are the whole API. Swap grid= for a grid_spec=; the prefetched arguments come first and get no BlockSpec; and both signatures gain them, in a fixed order: 

index_map(*grid_indices, *prefetch_refs)
kernel(*prefetch_refs, *input_refs, *output_refs, *scratch_refs)

"If num_scalar_prefetch is n, then the first n arguments to pallas_call will be placed in SMEM. No BlockSpecs should be specified for those arguments." (sparse.html). SMEM, not VMEM, because this is control data — the §6.2 rule of thumb.

2 · The table is lesson 01's predicate, compiled

Now the interesting part, which is not the API. What goes in the table?

splash_attention prefetches three arrays. Two of them matter here, and their definitions come straight out of the library's own docstring:

data_next: … each entry contains the next kv block index to prefetch.
block_mask: … entries can be 0, 1 or 2. An entry of 0 indicates that the corresponding block in the full mask was all zeros. An entry of 1 indicates that the corresponding block contained both zeros and ones. An entry of 2 indicates the corresponding block was entirely ones. — splash_attention_mask_info.py, MaskInfo
The win

That is lesson 01's trichotomy, verbatim, as an integer in SMEM. All zeros is dead; both zeros and ones is partial; entirely ones is full. The reference sheet you wrote in session 1 has the same three rows and the same two consequences — dead means do not load, full means do not mask. Google's production kernel encodes it as 0, 1, 2. You derived the classification before you knew what it was for; this is what it was for.

And the kernel spends it exactly where you would predict. One helper reads all three tables and returns the block index plus two booleans: 

is_nonzero      = block_mask_ref[h, i, j] > 0      # should_run
should_not_mask = block_mask_ref[h, i, j] != 1     # i.e. it is 2, a full block
next_j          = data_next_ref[h, i, j]           # which kv block to fetch

_next_nonzero, splash_attention_kernel.py. next_j is what k_index_map and v_index_map return; is_nonzero gates the compute; should_not_mask is passed to _apply_mask_and_soft_cap, which then skips the elementwise jnp.where entirely.

So 0 saves a fetch and a matmul, and 2 saves a mask pass. Two different savings from one table, which is why the classification has three values and not two.

3 · Shrink the grid

Now the second half. Row i of the mask has at most m live blocks — for Gemma's local layers with bkv = W = 512, that is two. Carrying a grid axis of length kv_len / bkv to run two useful steps is waste that no amount of copy elision removes, because the step still executes. So make the axis as wide as the busiest row and left-pack each row's live blocks into it: 

grid_width = fwd_mask_info.data_next.shape[-1]
grid       = (num_q_heads, q_seq_len // bq, grid_width)

splash_attention_kernel.py. The shrink itself is _shrink_mask_info in splash_attention_mask_info.py: per row, take the non-zero columns, then "pad each row … to match the width of the longest row. This avoids having jagged rows." A grid is a rectangle; that constraint never went away.

4 · Which half bought what

Read the three rows of that widget again at the default settings, because the difference between the last two is the thing most people get wrong:

index_mapgridstepscomputedK DMAs
returns j(4, 4)161616
returns data_next[i][j](4, 4)1674
same, shrunk axis(4, 2)874
The discriminator

The table buys the traffic. The shrink buys the steps. They are two independent optimisations that happen to arrive together, and either works without the other. Wire the table into index_map on a full rectangular grid and KV traffic already falls 16 → 4, because dead columns resolve to a neighbour's block index and lesson 03's rule elides the copy — but you still execute sixteen steps. Shrink the axis and the eight dead steps go, while the traffic does not move at all. If you can only say "block skipping made it faster", you cannot debug it when only one half is working.

And the traffic number is better than it looks. At the default geometry K costs 4 DMAs for 4 kv blocks: every key block is loaded exactly once for the whole layer. Not once per query row — once, full stop. The reason is visible in the kv index sequence,

i=0: 0, 0  ·  i=1: 0, 1  ·  i=2: 1, 2  ·  i=3: 2, 3
flattened   0 0 0 1 1 2 2 3

which never decreases. Row i ends on block i and row i+1 begins on block i, so the elision crosses the row boundary — the pipeline knows nothing about rows, only about consecutive steps. Every repeat collapses, and the count falls to the number of distinct blocks.

This is a property of the geometry, not of block skipping

It holds because W ≤ bkv makes each row's live set exactly {i−1, i}. Break that and the sequence stops rising. Set the widget to W = 1024 at B = 512: rows now overlap in two blocks, the sequence steps backwards at each boundary, and K DMAs go 4 → 8 against the same four distinct blocks. Worse, halve the block instead — W = 512, B = 256 — and it is 20 DMAs for 8 blocks. The reference sheet already told you halving B quadruples the grid; it did not tell you it also destroys the load-once property, because that fact needs the pipeline, and in session 1 you did not have it yet.

Check the highlighted row against arithmetic you did in session 1. Live tiles are R·m − m(m−1)/2 with R = 64 and m = W/B + 1 = 2, so 128 − 1 = 127. The reference sheet says 127. The kernel executes 127. The predicate and the pipeline agree, and the one spare step is the padding in row 0, which the table marks 0 so nothing runs in it.

6 · Three things the table does not do

Each of these has a specific cost, and none of them is optional:

  • It does not mask within a block. At W = B = 512 the widget's block_mask contains only 0 and 1 — no twos at all, because no 512×512 block sits entirely inside a 512-wide band. Every block you load still needs lesson 01's elementwise mask. Block skipping removes whole dead blocks; it never removes the mask.
  • It does not make a padded step free. A row with fewer live blocks than grid_width is padded, and block_mask = 0 stops the compute — but the pipeline still resolves that step's index_map and may fetch. The library pads data_next with 0, not with a repeat of the previous index, so a padded step after a high block index costs a genuine transfer. Harmless for a local layer, where only row 0 is short. Not harmless for a causal one.
  • It does not build itself. process_mask is host-side NumPy that materialises the mask block by block and reduces each one with .any() and .all(). That is fine when the mask is static and known at trace time — which for windowed prefill it is. It is not free for a mask that changes per call.

7 · Is the output still safe?

One thing should worry you. Lesson 03's accumulator works because "all invocations that write to a particular slice are consecutive". Shrinking a grid is exactly the kind of surgery that could break consecutiveness — so check it rather than assume it.

It holds, and the reason is structural: shrinking removes steps from inside a row and never permutes i. The output index_map returns i, so the output block is revisited grid_width times in a row, then never again. Confirmed by execution — a shrunk-grid kernel accumulating with o_ref[...] += … matches a dense masked reference to 8.7e-7 relative, under both interpreters. If revisits were not consecutive the partial sums would have been flushed and overwritten.

So why does splash_attention carry an o_scratch?

You asked this at the end of lesson 04. Now it can be answered from the source: because o_ref is not its accumulator. The running output lives in o_scratch_ref at f32 and is rescaled every inner step by the online-softmax factor — o_scratch_ref[:] = alpha_o * o_scratch_ref[:] + o_curr — and o_ref is written exactly once, on the last inner step, already normalised and already cast: o_ref[...] = (o_scratch_ref[...] * l_inv).astype(o_ref.dtype). Two reasons it has to be that way. The accumulator needs f32 while o_ref carries the caller's output dtype, and the division by ℓ can only happen once, at the end. So o_ref's residency is not being used to accumulate — it is being used to avoid grid_width − 1 pointless write-backs. Same residency, different reason.

Where this goes

You now have every piece of a windowed-prefill kernel: which tiles are load-bearing, what to do with one when it arrives, which axis keeps an operand resident, how big a block may be, and how to make the grid refuse the rest. What you do not have is a number. Phase 6 asks which roof binds — and block skipping is precisely the kind of change that moves a kernel from one roof to the other, because it cuts traffic and FLOPs by different factors. Cutting 4096 loads to 64 while cutting compute 4096 → 127 changes the arithmetic intensity, and that is the next thing worth being able to compute.
