Lesson 03 · Windowed prefill

Which axis goes last

Two nested loops, same twelve steps, same arithmetic. Order them one way and you move three blocks of queries. Order them the other way and you move twelve. Nothing in the kernel body changed.

Lesson 01 decided which tiles are worth loading. Lesson 02 decided what to do with one once it arrives. Neither said a word about what actually moves the data. That is this lesson, and it turns out to hinge on a single structural choice you make before writing any kernel body at all.

1 · Twelve steps, two ways

(8, 128) blocks because TPU wants that shape — the rule and the reason are lesson 04. Take the numbers on faith for one lesson; nothing here depends on them.

Your kernel walks query blocks on the outside and key blocks on the inside — three of the first, four of the second. In Pallas that is a grid, and each operand gets a BlockSpec saying which slice of it this step needs: 

pl.pallas_call(
    kernel,
    grid=(3, 4),                                      # i_q outer, j_kv inner
    in_specs=[
        pl.BlockSpec((8, 128), lambda i, j: (i, 0)),  # Q — ignores j
        pl.BlockSpec((8, 128), lambda i, j: (j, 0)),  # K — follows j
    ],
)

Twelve steps. Q is used at every one of them, K is used at every one of them. Here is what each step actually costs in traffic:

Q: 3 copies. K: 12. Now swap the two grid axes — keep the block shapes, keep every index_map pointing at the same data, change nothing but which loop is on the outside:

gridQ copiesK copiessteps
(3, 4) — i_q outer31212
(4, 3) — j_kv outer12412

Same twelve steps, same block shapes, same FLOPs, 4× the Q traffic. The rest of this lesson is why, and how to see it coming.

2 · Three facts, and the numbers follow

First: the operands are not where the kernel thinks they are.

The default behavior for pallas_call on TPU is that arguments to pallas_call are assumed to live in HBM, and inputs to the user kernel body are stored in VMEM. — TPU Pipelining · TPU Memory Spaces

So every ref your kernel body touches is a VMEM buffer that something had to fill by DMA from HBM. Counting copies is counting the kernel's bandwidth bill.

Second: the grid is a loop nest, and the last axis is the inner loop.

pl.pallas_call(some_kernel, grid=(n, m))(...) is equivalent to
for i in range(n): for j in range(m): some_kernel(...) — Grids and BlockSpecs

And on TPU that nesting is a guarantee rather than a hint — "TPUs are actually highly sequential machines… the grid is generally not processed in parallel, but sequentially, in lexicographic order" (Writing TPU kernels with Pallas). You may rely on the order. That matters, because the third fact is entirely about what consecutive means.

Third: index_map returns block indices, not element offsets.

the index_map … takes as arguments the invocation indices … and returns block indices (one block index for each axis of the overall array). Each block index is then multiplied by the corresponding axis size from block_shape to get the actual element index. — Grids and BlockSpecs · BlockSpec

lambda i, j: (i, 0) does not mean "row i". It means "block i down, block 0 across" — element row 8i, since the block is 8 tall. Two things worth noticing about that lambda, and both are the lesson:

  • It is a function of the loop counters, evaluated fresh at every grid step.
  • It ignores j. Across all four values of j, it returns the same answer.

3 · The rule

Everything above is setup for one sentence, and it is stated outright in the docs:

When two (lexicographically) consecutive grid indices use the same slice of an input, the HBM transfer for the second iteration is skipped, as the data is already available. — Writing TPU kernels with Pallas

Said a second way, in the pipelining guide, with the mechanism named: "if the data slices between two consecutive iterations are the same, the pipeline will not issue a copy_in/copy_out on that buffer… the same SRAM buffer used in a previous iteration will be passed into the kernel again" (Software Pipelining).

Now go back to §1 and the numbers are forced. j is the fast axis. Q's index_map ignores j, so for four consecutive steps it returns the same block index and three of the four copies are skipped — 3 DMAs, not 12. K's index_map follows j, so it changes at every single step and nothing is ever skipped.

The win

index_map decides residency, not just addressing. An operand stays in VMEM across a run of steps exactly when its index_map ignores the fastest-varying grid axis. Which axis is fastest is the last one in the grid tuple. So the operand you cannot afford to re-fetch determines which axis goes last — that is the decision, and you make it before you write a line of the kernel body.

The trap in "swap the axes"

Swapping grid=(3, 4) to grid=(4, 3) silently renames the lambda's parameters. The first positional argument is now j_kv, not i_q. Q's spec has to become lambda j, i: (i, 0) — same mapping, different signature. Leave it as lambda i, j: (i, 0) and you have not reordered a loop, you have pointed Q at the wrong data, and it will run.

5 · Outputs look the other way

You will have noticed O in that widget behaves like Q — one write-back per query block, not one per step. That is the same rule, applied in the opposite direction, and the asymmetry is exactly right:

buffercopies when
inputfirst step, or the block index changed since the previous step
outputlast step, or the block index will change on the next step

Both predicates are visible in JAX source, in two independent implementations that agree — the interpreter and pltpu.emit_pipeline. See research 0001 §3.4.

Inputs look backwards; outputs look forwards. The consequence is the one that matters to you: when an output block is revisited on consecutive steps, the same VMEM buffer comes back, un-flushed, still holding what you wrote. It is an accumulator. And now lesson 02 lands in a place you were not expecting it:

m, ℓ, O accumulate across kv tiles
⇒ the output block index must not vary along the kv axis
⇒ kv must be the last grid axis
⇒ Q is resident, K and V stream past it

The online-softmax recurrence does not merely permit that grid order. It requires it. And having required it, it hands you the Q residency for free. The docs impose the same thing from the other side — "Reduction/accumulation should only be performed over the last (innermost) dimensions of the grid, and the buffer should be initialized manually first" (Software Pipelining).

Put the reduction on a leading axis instead and the revisits are no longer consecutive, so every one of them round-trips through HBM and the accumulation is lost. Run in interpret mode, that kernel returns NaN — uninitialised VMEM, never zeroed, never accumulated. Two bugs surfacing as one number.

Verified, not asserted

The copy counts on this page were produced by execution, on CPU, under Pallas interpret mode — by writing a per-step sentinel into an input buffer and checking whether it survived. Two honest caveats. One: writing to an input ref is something the docs explicitly forbid ("input buffers … should be interpreted as read-only") — it is an instrument here, not a technique; do not ship it. Two: interpret mode is not hardware. The pipeline that runs on a v5e is emitted by the Mosaic compiler, not by the Python you can read, and jax-ml/jax#36287 exists to remind you the two can diverge. What is solid: the skip is documented behaviour in two places, and two JAX-authored implementations honour it. What is not measured: DMA counts on a real chip.

Where this goes

Two things were taken on faith here and are owed to you. Why (8, 128) — TPU's block-shape rule, what it costs when your shapes do not divide, and the fact that interpret mode will not catch a violation. And whether the blocks fit at all — the VMEM budget, which is where double buffering stops being free and starts being a number you multiply by two. That is lesson 04.

After that, Phase 5: this grid is still walking every kv block. Lesson 01 said most of them are dead. Making the grid skip them is where the mask predicate finally becomes an index_map — and per ADR-0001, that ordering is deliberate.
