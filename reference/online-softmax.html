Online softmax

Computing an exact softmax in one pass, holding one tile of scores at a time — the recurrence, the invariant that tests it, and the four ways it goes wrong.

The recurrence

Per query row. Tiles of scores S1 … ST with matching value tiles Vj. State is three things: m scalar, ℓ scalar, O vector of head_dim.

init   m0 = −∞  ·  ℓ0 = 0  ·  O0 = 0

mj = max(mj−1, rowmax Sj)
αj = emj−1 − mj   (old minus new)
Pj = eSj − mj
ℓj = αj·ℓj−1 + rowsum Pj
Oj = αj·Oj−1 + Pj Vj

finalise   answer = OT / ℓT   (divide once, at the end)

Source: Milakov & Gimelshein 2018, Algorithm 3 (the ℓ half, proved by induction); FlashAttention §3.1 Algorithm 1 (the same recurrence with O attached).

The invariant

ℓj = Σseen es − mj  ·  Oj = Σseen es − mj v  ·  Oj/ℓj = exact attention over tiles 1…j

Every intermediate state is a finished answer to a smaller problem, not a partial one. Assert this per tile in interpret mode — it localises a bug to the tile that caused it instead of to the final output.

Why the running max

PropertyComes fromWhat it buys
exactnessthe algebra alone nothing to do with the max — ea−b distributes over a sum for any sequence mj
runningthe single pass the global max is not available; whatever you subtract must be computable from tiles already seen
maxfloating point every exponent ≤ 0 ⇒ every term in (0, 1] ⇒ overflow impossible by construction
α ≤ 1m non-decreasing the rescale only ever shrinks; a factor above 1 would amplify accumulated error once per tile

Stated as one line: "running" comes from the algorithm, "max" comes from the hardware. Freezing m keeps the answer exact and destroys the range.

Verified with ml_dtypes. bf16 trades mantissa for float32's exponent range, so the overflow ceiling is the same — which is why bf16 is the accelerator format and fp16 is not. Accumulate m, ℓ, O in float32 regardless.

Traps

Trap 1 · rescaling ℓ but not O

Both accumulated under the old max; both take the same α. Rescale only ℓ and the denominator is right while the numerator is stale — the output is wrong by a per-row factor, which reads like a precision problem and is not.

Trap 2 · the sign of α

α = emold − mnew. Old minus new, so the exponent is ≤ 0. Inverting it gives a factor ≥ 1 that inflates the accumulator every time the max moves. Derive the direction from m being non-decreasing rather than memorising it.

Trap 3 · a fully-masked tile poisons the row

If every score in a tile is −∞ and m is still −∞, then α = e−∞ − (−∞) = eNaN = NaN, and NaN propagates through the rest of the row. Verified reachable in this project: at N = 512, W = 256, B = 256, the tile q ∈ [256,511] × k ∈ [0,255] is partial — but query row 511 has zero allowed keys in it, and that is the first key tile it visits. Checked against reference.attention_mask(512, 512, window=256).

Fix: guard the first step (α := 0 when mj−1 = −∞), or skip tiles that are dead for this query row and not merely for the tile as a whole. Block skipping alone does not save you — this tile is live.

Trap 4 · dividing per tile

O is unnormalised until the pass ends. Divide once, after the last tile. Dividing per tile means re-multiplying to undo it, and loses bits each time.

Rescaling O is a scalar–vector multiply, not a matmul — that is what makes the scheme affordable. For a block of Bq query rows, m and ℓ are vectors of length Bq and O is Bq × head_dim; every operation above is row-wise.

Cost per tile

1 rowmax  ·  1 exp over the tile  ·  1 rowsum  ·  2 scalar rescales  ·  1 PV matmul

A row visiting n live tiles pays n − 1 real rescales — the first tile initialises from nothing. Live tiles per row come from block-skipping arithmetic: W/B + 1 for a local layer, so W/B rescales.
