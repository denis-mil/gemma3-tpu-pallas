Block shapes and the VMEM budget

How big a block may be, and whether it fits — the two checks Mosaic makes at compile time and no CPU makes at all. Apply both by hand, before you burn TPU quota.

The shape rule

Applies to block_shape in a BlockSpec. Only the last two axes are constrained; leading axes are free.

rank ≥ 2  ⇒  ( blk[−2] = arr[−2] or 8 | blk[−2] )  and  ( blk[−1] = arr[−1] or 128 | blk[−1] )

rank = 1  ⇒  blk[0] = arr[0]  or  1024 | blk[0]  or  blk[0] = 2k ≥ 128·(32/bitwidth)

Source: Grids and BlockSpecs. The rank-1 floor is 128 for f32, 256 for bf16, 512 for int8.

The rule as written is ambiguous — do not resolve it silently

"the last two dimensions … must be equal to the respective dimension of the overall array, or be divisible by 8 and 128 respectively" reads two ways. Per-axis (above) lets each axis pick its own escape. Paired requires both to match or both to divide. They split exactly when one axis is satisfied by equality and the other by divisibility: (8, 7) on (16, 7) is legal per-axis and illegal paired. Nothing in the docs decides it and no CPU can. Treat such a shape as illegal until hardware says otherwise.

Why 8 and 128

Namev5eIs
sublanes8second-minor axis of a vector register

MXU column size128matmul unit width — a different 128

Vector computation is padded up to the tile size. An 8×128×1×1 array is padded to 8×128×8×128 and costs 1024× an 8×128 one (Array Layouts). Two consequences, both load-bearing:

  • A singleton trailing dimension is width you already paid for. (bq, 1) occupies the same tiles as (bq, 128). This is why splash_attention declares m and ℓ as (bq, 128) and broadcasts rank-1 inputs out to the lane count.
  • Trailing dimensions of size 1 are a design smell, not an optimisation.

Non-dividing blocks

Legality and divisibility are separate questions. A legal block that does not tile the array evenly is allowed, and behaves like this:

WhatHappens
tail block inputpadded with unspecified garbage — NaN under interpret mode, and the docs say not to rely on it
tail block outputout-of-range elements discarded
the gridstill runs every step. Padded blocks are fetched, computed, thrown away. Full traffic, full FLOPs
your maskstill required. Padding pads the shape; it does not neutralise the values

At least one element of every block must be in bounds, so a block wholly past the end is rejected rather than skipped. Garbage in a score tile reaches lesson 02's running max: a single +inf in padding takes the entire query row with it.

The VMEM budget

pallas_call accepts only buffer counts 1 and 2 — lowering.py rejects anything else. Larger counts and lookahead are pltpu.emit_pipeline features.

The two regimes

For flash-style attention with square blocks b, head_dim d, bf16 in and f32 accumulators:

operands + scratch ≈ linear in b  ·  score tile = 4·bq·bkv bytes = quadratic in b
RegimeDoubling bThe knob that matters
below crossover≈ doubles VMEMbuffer count — the ×2 from double buffering
above crossover≈ quadruples itbq × bkv; decouple pipeline block from compute block

"Which regime am I in" is the question that transfers. A single total does not. For Gemma 3 1B (d = 256, MQA, window 512) the linear coefficient is 6144 B per unit of b and the crossover is b = 1536 — so at the window's own 512, the kernel is firmly linear and the ×2 is the term to argue about.

Query these yourself, offline, no accelerator needed:
pltpu.get_tpu_info_for_chip(ChipVersion.TPU_V5E, 1). The published hardware reference is generated from the same call, so page and source cannot drift.

VMEM on v5e is contested inside JAX's own repo

details.rst says "16MB+" (generation-agnostic, and exactly the v4 figure, on a page with no reviewed-date). tpu_info.py says 128 MiB. The v5p figure is quoted as 96 MB on one JAX doc page and 64 MiB in JAX source — a flat contradiction in one repository. Cloud's v5e page never mentions VMEM at all.

Use tpu_info.py: machine-readable, versioned, and it generates the docs. But say which you used, and check whether the answer even depends on it — the largest square block that fits is b ≈ 1419 under 16 MiB and b ≈ 5075 under 128 MiB, so for any block near the 512 window the disagreement changes nothing.

The failure mode

Exceeding VMEM is a compile-time error from Mosaic, not a runtime OOM, and the docs promise only "a low-level compiler error message complaining about an out-of-memory error". Nobody in this workspace has seen one; capture it verbatim the first time it happens.

Neither published number is your real budget

pltpu.CompilerParams(vmem_limit_bytes=…) "must be used in conjunction with the --xla_tpu_scoped_vmem_limit_kib=N flag". So the budget a kernel actually gets is an XLA scoped limit, not the physical capacity. The default value of that flag is not stated anywhere in the JAX Python tree — an open gap in RESOURCES.md.

Pre-flight, before spending TPU time

Everything below is invisible from CPU. Interpret mode allocates ordinary host arrays: it will accept an illegal block shape and happily "fit" a block no TPU could hold.

#Check
1Trailing two axes of every block_shape satisfy the rule — and none is ambiguous under the two readings
2No trailing dimension of size 1 that could have been 128
3Blocks that do not divide: the mask covers the padded tail
4Σ (block × itemsize × buffers) + score tile, against a ceiling you can name
5Whole-array operands actually declared so lowering can single-buffer them
6Accumulation on the last grid axis — otherwise it is not an accumulator at all

Checks 1 and 4 are mechanised in lesson 04's two widgets. Check 6 is lesson 03.
