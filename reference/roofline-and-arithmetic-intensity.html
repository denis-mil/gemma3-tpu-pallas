Reference sheet

Roofline and arithmetic intensity

Everything needed to say which roof binds a TPU v5e kernel, and the arithmetic to back it — with the constants, their sources, and the disagreements between them.

The model

intensity I = FLOPs ÷ bytes moved to/from HBM
attainable FLOP/s = min( P,   I × β )   ·   ridge I* = P ÷ β
time floor = max( FLOPs ÷ P,   bytes ÷ β )

I < I* memory-bound · I > I* compute-bound. Source: Williams, Waterman & Patterson, UCB/EECS-2008-134, 2008.

I is a property of the algorithm and its schedule; I* is a property of the chip alone. Changing BlockSpecs changes I. That is the whole reason a roofline is actionable rather than descriptive.

Trap · the bandwidth is not agreed

Cloud TPU v5e says 800 GiBps, which is 858.99e9 B/s — 4.8% above JAX's 820e9. The same table writes HBM capacity as “16 GB” where tpu_info records 17,200,000,000 bytes, i.e. 16 GiB, so its GB/GiB labelling is loose. Take 820e9 and carry 229–241 as the ridge's range. Then check whether the range changes your answer — at any sane block size it does not, and saying that is a stronger claim than quoting one constant.

Both roofs, offline, in two lines

from jax._src.pallas.mosaic import tpu_info as ti
ti.get_tpu_info_for_chip(ti.ChipVersion.TPU_V5E, 1)

Returns bf16_ops_per_second, mem_bw_bytes_per_second, vmem_capacity_bytes, smem_capacity_bytes, hbm_capacity_bytes, num_mxus, mxu_column_size, num_lanes, num_sublanes. Chip versions are the ti.ChipVersion enum (TPU_V4 … TPU_V6E); the second argument is TensorCores per logical device, 1 for v5e. No accelerator required — this is a table in the JAX tree, not a device query.

Mnemonic, not a derivation

4 MXUs × 128 × 128 × 2 FLOPs × 1.5 GHz ≈ 197 TFLOP/s, which is a useful way to remember that the compute roof assumes all four MXUs fed with 128-wide tiles every cycle. Do not promote it to a formula: the same arithmetic on v6e's table entries (2 MXUs × 256, 920 TFLOP/s) implies 3.5 GHz, which is not a real clock. The assumption is the part worth keeping — it is the block-shape rule wearing a different hat.

Counting an attention layer

Grid (head, q_block, kv_block), kv innermost, bf16 operands, all four operand blocks (B × D). Let R = N/B query rows, L live blocks per head, k K-DMAs per head after copy elision, H query heads, D = head_dim:

FLOPs = 4 · H·L · B² · D   ·   bytes = 4H·(R + k) · B · D
I = L · B ÷ (R + k)

4H(R+k) is Q read once per (head, q_block), O written once, and K and V fetched k times each per head — the head axis being outermost means MQA's single KV head is streamed H times, not once.

The two closed forms worth remembering

Phaseintensitybecause
prefill, W ≤ B≈ BL = 2R−1, k = R ⟹ I = B(2R−1)/2R
decode, MQA/GQA= HW and D cancel; only the sharing ratio survives

So a prefill kernel's intensity is the block size, and a decode kernel's is the number of query heads per KV head. Against a ridge of 240 that settles both cases immediately: B = 512 clears it 2.1×; H = 4 misses it 60×.

The two invariances worth carrying to the next kernel

Block skipping cannot change which roof binds. A dead block takes its load and its compute away together, so FLOPs and bytes fall by the same factor and the ratio survives. Skipping is worth 32× in time and 1.008× in intensity.

An optimisation that only cuts bytes buys nothing above the ridge. Sharing MQA's KV stream across heads lifts intensity 508 → 813 and moves the floor by zero microseconds, because the compute roof was already binding. Check the regime before writing the optimisation.
