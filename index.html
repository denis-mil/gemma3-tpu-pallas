gemma3-tpu-pallas · Teaching workspace

Windowed attention on a TPU, worked out from first principles

Six lessons and five reference sheets on writing a Pallas attention kernel for Gemma 3 1B — derived at the shapes the model actually runs, on a single TPU v5e.

Gemma 3 interleaves local and global attention layers: 22 of the 1B model's 26 layers see only a 512-token window. At a 32K prompt a local layer computes about 64× more score pairs than it keeps, so the interesting kernel is not one that masks that work away but one that never loads it. Everything here is an attempt to say precisely which tiles those are, and what refusing them is worth.

Status

Scaffolding, arithmetic and references are complete — no kernel is written yet. The numbers below are derived and, where a CPU can check them, tested; none has run on a chip. Each page names its instrument before it states a boundary. Source: github.com/denis-mil/gemma3-tpu-pallas.

Lessons

Read in order — each one leaves a debt the next collects.

  1. Lesson 01 · Windowed prefill The mask is a work map

    A mask tells you which scores to throw away. Read it one tile at a time and it tells you something far more useful: which memory you never had to load.

  2. Lesson 02 · Windowed prefill The normaliser you don't have yet

    Softmax needs a denominator over every score. A flash kernel only ever holds one tile of them. The fix is not an approximation — it is an accumulator you are allowed to correct after the fact.

  3. Lesson 03 · Windowed prefill Which axis goes last

    Two nested loops, same twelve steps, same arithmetic. Order them one way and you move three blocks of queries. Order them the other way and you move twelve. Nothing in the kernel body changed.

  4. Lesson 04 · Windowed prefill Two rules your CPU won't enforce

    Lesson 03 took (8, 128) on faith and never asked whether the blocks fit. Both debts come due here — and both are checks that your only available machine will silently decline to make.

  5. Lesson 05 · Windowed prefill The index_map that lies

    Lesson 01 derived which tiles a windowed kernel may refuse to load. Four lessons later that predicate has still never run. This is where it becomes code — and the machinery it needs turns out to be machinery you already have.

  6. Lesson 06 · Windowed prefill The roof that didn't move

    Lesson 05 ended with a prediction: block skipping cuts loads and compute by different factors, so it should move the kernel from one roof to the other. This lesson works out the arithmetic. The prediction is wrong — and the reason it is wrong is worth more than the roofline itself.

Reference sheets

The formulas, constants and failure modes, stripped of the derivations. Written to be returned to rather than read through.

  • Reference sheet Block-skipping arithmetic

    Everything needed to decide, at trace time, which tiles a windowed attention kernel must load — and how much it costs to get the block size wrong.

  • Reference sheet Online softmax

    Computing an exact softmax in one pass, holding one tile of scores at a time — the recurrence, the invariant that tests it, and the four ways it goes wrong.

  • Reference sheet Block shapes and the VMEM budget

    How big a block may be, and whether it fits — the two checks Mosaic makes at compile time and no CPU makes at all. Apply both by hand, before you burn TPU quota.

  • Reference sheet Scalar prefetch and shrunk grids

    How a mask predicate becomes an index_map. The API, the two table constructions, the kernel skeleton, and the numbers each half actually buys.

  • Reference sheet Roofline and arithmetic intensity

    Everything needed to say which roof binds a TPU v5e kernel, and the arithmetic to back it — with the constants, their sources, and the disagreements between them.
